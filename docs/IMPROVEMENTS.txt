LPMS - CODE IMPROVEMENTS
========================
File changed   : main.cpp
Files untouched: password-generator/*, test_acc/users.txt, existing vault .txt files
All line numbers below refer to the BEFORE state, i.e. main.cpp before this change.


IMPROVEMENT 1 - A saved entry's email can no longer be modified
---------------------------------------------------------------
Before (modifyPassword, lines 387-394):
    Credential& cred = credentials[selected];
    const Credential original = cred;
    cout << "Modifying [" << original.appName << "] information for " << original.email << "\n";
    cout << "Leave a field blank to keep its current value.\n";
    cout << "Email (" << original.email << "): ";
    getline(cin, input);
    if (!input.empty()) cred.email = input;

    The flow let the user overwrite the email that was linked to a saved
    password, and there was no validation on the new value at all.

After (modifyPassword, lines 567-572):
    Credential& cred = credentials[selected];
    cout << "Modifying entry " << (selected + 1) << " of " << credentials.size() << "\n";
    cout << "Website: " << cred.appName << "   (cannot be changed)\n";
    cout << "Email: " << cred.email << "   (cannot be changed)\n";
    cout << "Only the password can be modified.\n";

    The email prompt is gone. Nothing in modifyPassword assigns cred.email
    or cred.appName any more, and the removed `original` copy is no longer
    needed. The screen now states both locked fields instead of prompting
    for one of them.

Reason:
    A saved record is identified by the website/email pair; the password is
    the only part that actually rotates. Changing the email silently turned
    the entry into a different account while keeping the old password, which
    is exactly how a manager confuses a user. Locking it also removes the
    only write path to cred.email in modifyPassword, so an entry can no
    longer diverge from the email it was created for. To move a password to
    another email, the user deletes the entry and adds it again, which keeps
    one deliberate, visible action per change.


IMPROVEMENT 2 - Strict accepted format for website names
---------------------------------------------------------
Before (addPassword, lines 139-140):
    cout << "Enter Website Name: ";
    getline(cin, cred.appName);

    Any text was accepted: empty lines, "My Site", "http://x.com",
    "Google", or a string containing "] " that breaks the vault format.

After (new isValidHostname / isValidWebsiteName / readWebsiteName,
lines 129-248; used by addPassword line 342):
    cout << "Enter Website Name (e.g. Google.com or x.com): ";

    Accepted only when all of these hold, after trimming surrounding spaces:
      - length 4 to 253 characters
      - contains at least one '.', and the last label (TLD) is 2+ letters
      - every label is 1-63 characters of A-Z a-z 0-9 and '-', and does not
        start or end with '-'
      - no '@', whitespace, '/', ':', '|', '[' or ']' anywhere
      - the same website is not already saved for this user, compared
        case-insensitively

    Examples: Google.com, x.com, mail.google.co.uk  -> accepted
              Google, My Site, http://x.com, x@y   -> rejected, reprompt
    Case is kept as typed, so the list shows "Google.com", not "google.com".

Reason:
    Data integrity and consistency. The vault is a flat text file in the
    form "[app] email | password", so a name with ']' or '|' corrupts every
    later line, and duplicates make two entries indistinguishable when the
    user later picks one by number. Requiring a dot and a letters-only TLD is
    what makes "Google.com" and "x.com" comparable instead of free text.
    Because only new input is validated, entries already in the file are
    never rejected or rewritten.


IMPROVEMENT 3 - Strict accepted format for emails
-------------------------------------------------
Before (addPassword, lines 149-151):
    cout << "Enter custom email for " << cred.appName << ": ";
    if (!getline(cin, cred.email)) return;

After (new isValidEmail / readEmail, lines 188-267; used by addPassword
line 353):
    Accepted only when all of these hold, after trimming surrounding spaces:
      - exactly one '@'
      - local part 1 to 64 characters of A-Z a-z 0-9 . _ % + -
      - local part does not start or end with '.', and has no ".."
      - domain part follows the same rules as a website name (dot + TLD)
      - total length 254 or less
    Rejection message: "Invalid email. It needs exactly one '@' and a
    domain, e.g. user@example.com." followed by a blank line and a reprompt.

Reason:
    Same integrity argument as IMPROVEMENT 2: an email without '@' cannot be
    told apart from a website name in the "Search website or email" box, and
    a stray '|' or ']' would break the vault line. The rule is applied only
    to newly typed emails; the logged-in account from test_acc/users.txt is
    never re-validated, so existing test accounts keep working.


IMPROVEMENT 4 - The (y/n) prompt is more forgiving and better spaced
---------------------------------------------------------------
Before (promptYesNo, lines 82-101):
    The loop and the "Invalid input. Please enter 'y' or 'n'." message were
    already there - an invalid answer did NOT fall through. The real gaps
    were narrower:
      - only the exact strings "y", "Y", "n", "N" were accepted, so "yes",
        "no", " y" and "y " were all treated as invalid
      - the error was printed with a single endl, so it sat directly under
        the typed answer with no blank line around it:
            Do you want to generate a new password? (y/n): maybe
            Invalid input. Please enter 'y' or 'n'.
            Do you want to generate a new password? (y/n):

After (promptYesNo, lines 107-127):
    while (true) {
        cout << prompt;
        string choice;
        if (!getline(cin, choice)) return false;
        choice = lowercaseText(trimText(choice));
        if (choice == "y" || choice == "yes") { answer = true;  return true; }
        if (choice == "n" || choice == "no")  { answer = false; return true; }
        printInputError("Invalid input. Please enter 'y' or 'n'.");
    }
    Input is trimmed and lowercased, "yes"/"no" are accepted, the rejection
    now has blank lines around it, and every caller still gets false on EOF
    so the operation aborts instead of spinning on a closed stream.

Reason:
    One shared prompt is used by logout, add, modify and delete, so hardening
    it once fixes all of them. Trimming means a stray leading or trailing
    space no longer counts as an error, and accepting "yes"/"no" matches how
    people actually answer a question. This is a polish item, not a bug fix:
    the previous version was already safe, it was just stricter and tighter
    on screen than it needed to be.


IMPROVEMENT 5 - Readable spacing after every rejected input
-----------------------------------------------------------
Before:
    Each error was printed on the prompt line or with a single "\n":
        cout << "Invalid input. Please enter 'y' or 'n'." << endl;      (line 99)
        cout << "\nInvalid menu choice. Please choose 1, 2, 3, 4, or 0.\n"; (line 471)
    so the retry prompt sat immediately under the error text.

After (new printInputError, lines 101-105):
    void printInputError(const string& message) {
        cout << "\n" << message << "\n\n";
    }
    One blank line above the message and one below it, so the retry prompt
    is visually separated from the error. Used by promptYesNo,
    readWebsiteName, readEmail, choosePasswordLength and the main menu loop.
    Example:
        Enter Website Name (e.g. Google.com or x.com): My Site

        Invalid website name. Use a plain domain such as Google.com or x.com
        (no spaces, no http://, and it must end with letters like .com).

        Enter Website Name (e.g. Google.com or x.com):

Reason:
    Readability. Without the blank lines the error and the next prompt read
    as one block, and it is easy to retype into the wrong line. Routing every
    message through one helper also keeps the spacing identical everywhere.


IMPROVEMENT 6 - Password length: default first, then custom, with reprompt
--------------------------------------------------------------------------
Before (addPassword, lines 161-180):
    cout << "Enter desired length (default 12, min 8, max 25): ";
    ...
    if (!validLength) {
        cout << "Invalid or missing length. Using the default length of 12.\n";
        options.length = 12;
    }

Before (modifyPassword, lines 405-419): the same block again, but it fell
    back to 12 silently, with no message at all.

After (new choosePasswordLength, lines 269-304; used by addPassword line 365
and modifyPassword line 584):
    Use the default password length (12 characters)? (y/n):
      y -> 12 characters
      n -> Enter desired password length (min 8, max 25):
             a value outside 8-25 or a non-number now reprompts with
             "Invalid length. Please enter a whole number between 8 and 25."
             instead of quietly using 12

Reason:
    Most users want the default, so making them read a length question and
    press Enter every time is a needless decision. Asking about the default
    first turns the common case into one keystroke and only shows the numeric
    prompt to users who actually want a custom length. Silently substituting
    12 after an invalid entry is the one behaviour worth removing: the user
    believed they chose a length and got a different one, which is a real
    problem for a password. It also removes the duplicated block, so add and
    modify can no longer drift apart. Note passwordOptions::length defaults
    to 8 in password-generator/passwordgen.h, so the helper always sets the
    value explicitly.

KNOWN ISSUE, NOT FIXED (out of scope)
-------------------------------------
loadSavedPasswords splits each line on " | ", so a manually typed password
that itself contains " | " is truncated the next time the file is rewritten.
Email validation now blocks the ']' variant of this corruption, but not the
" | " one. Fixing it means changing the on-disk format, which would need a
migration step for existing vault files.
